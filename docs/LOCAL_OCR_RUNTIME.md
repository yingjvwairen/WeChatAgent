# 本地 OCR 的部署、进程复用与身份识别

`recognizeImage({file,backend:'rapidocr'})` 默认复用项目自己的本地 OCR 进程。识别前仍核对整个输入文件的 SHA256，输出保持原图尺寸与坐标。文字、置信度、联系人唯一性、账号绑定和界面稳定性校验没有降低。

微信联系人流程在获取焦点之前同时预热 small 和 medium。`warmLocalOcr({model:'small'|'medium',signal})` 校验固定 RapidOCR 3.10.0、ONNX Runtime 1.31.0 和相应三个模型的固定 SHA256，并加载模型会话；它不读图片、截图或操作窗口。small 检测、方向和识别模型随固定 RapidOCR 包安装，medium 识别模型由下面的部署入口准备。模型缺失、损坏或初始化失败时，在借用桌面前停止；推理期间不下载文件。

本机或副机运行 `scripts/prepare-ui-components.ps1` 时，会在安装 `requirements-ocr.txt` 后自动执行 `prepare-local-ocr-model.mjs --download`。模型保存到项目的 `state/ocr/models/PP-OCRv6_rec_medium.onnx`。已有正确文件只做本地校验；独立检查不联网，也不创建目录：

```text
node scripts/prepare-local-ocr-model.mjs --check
node scripts/prepare-local-ocr-model.mjs --download
```

下载使用 [RapidAI 官方 ModelScope 仓库的固定提交](https://www.modelscope.cn/models/RapidAI/RapidOCR/resolve/d298462ac20a2e994f433151b5fe6cc1180e9a09/onnx/PP-OCRv6/rec/PP-OCRv6_rec_medium.onnx) `d298462ac20a2e994f433151b5fe6cc1180e9a09`（RapidOCR 3.10.0 对应版本），固定大小为 76,629,984 字节，SHA-256 为 `eef444829dbbe18d7fea59a3f6eb75647518d2b3a9568d27c92e42940204894b`。此摘要也与 RapidOCR 3.10.0 包内 `default_models.yaml` 及本项目推理启动器一致。下载和重定向只接受 HTTPS，保留正常证书校验；限制大小、跳转次数与总时间，先写随机临时文件，完整验证后才替换目标。失败不覆盖原文件；路径中的符号链接或目录联接拒绝。

工作进程仅使用父子进程的 stdin/stdout NDJSON，不监听任何端口。协议包含版本、随机请求编号、原始图片摘要和有限可选参数。每个模型最多一个进程，最多同时排队四次读取。请求超时、取消或协议异常会终止相应进程并拒绝尚未完成的请求，不自动重放；15 秒空闲释放，父 Node 进程退出也会终止它。每次新建进程重新检查版本和模型摘要。`persistent:false` 保留独立一次性调用，供隔离诊断与比较。

可选 `region:{left,top,right,bottom}` 仅在 RapidOCR 后端支持；必须是原图内的完整整数矩形。Python 实际裁剪后识别，将所有框偏移回原图坐标，仍返回原图 SHA256 和尺寸；JS 再核对矩形与边界。Windows OCR 未实现区域识别，传入区域会明确拒绝。

另有显式白名单参数 `preprocess:'gray-gamma-1.6'`，用于原图中文字被颜色高亮影响的受控重识别。算法固定为 BGR 灰度加权 `round(B×0.114+G×0.587+R×0.299)`，再查表 `round((gray/255)^1.6×255)`，重复为三个通道。不接收自定义gamma、联系人文本或其它算法；不缩放、改坐标、补字符或重写置信度。原 PNG/JPEG 文件不改写，输入与输出仍绑定原图 SHA256，响应必须回显与请求完全相同的 `preprocess`，否则拒绝并关闭工作进程。省略此参数保持原流程；该变换不全局默认启用，也不代表身份已验证。严格身份校验仍由调用方按真实 OCR 输出执行。

微信联系人首次识别仍使用完整图和 small 模型。仅当原识别已经读出同一完整微信号、正确私聊分类与三行结构，而置信度未达原门槛时，才对同一原图标定的完整搜索结果区域使用 medium 模型重识别一次。区域包含分类、姓名和完整微信号，不使用搜索输入框证明目标身份。此路径不做灰度变换，仍核对原图摘要、尺寸、精确区域、模型标识、完整文本和所有原阈值，点击前重新检查区域像素，打开会话后还要核对资料身份。错误身份、群聊或再次低置信度都停止。

自动布局的搜索 OCR 使用同一完整原图中已证明的不透明内容体（opaque content body），包含分类、姓名及完整微信号。底部水平圆角必须在已验证的半径内回到内部背景；外侧整条混合边线不能成为另一个更高的内容体候选。两个不同完整内容体仍按歧义拒绝，不按面积选择。OCR 区域不包含的混合边线与阴影仍属于完整原生浮层像素摘要，重新打开后的完整浮层复验和点击前原生检查继续覆盖它们；区域定位不授予输入或身份权限。

相同像素裁剪会改变模型内部缩放，所以不能仅凭速度选算法。2026-10-27 的三张真实失败截图经此 medium 区域重识别后，完整 ID 最低置信度均达到 0.99978，单次约 2.8 秒；此前通过的样本仍仅使用原 small 完整图。四张静态样本的正式识别流程均通过，完整联系人导航随后也在本机实测通过。测试图片和私人 OCR 原文只留在本机诊断目录，不加入源码。

同一静态截图上，独立进程整图平均约 2306 毫秒；完整图复用进程并提前预热后，三次平均约 1227 毫秒，所有 306 个词的文本、坐标和置信度与原完整图结果逐项一致，身份校验三次通过。预热约 939 毫秒。这是本机离线样本测量，不代表联系人准备总耗时或所有图片的性能保证。

离线验证：

```text
node --test scripts/test-local-ocr-model.mjs scripts/test-local-ocr-client.mjs scripts/test-visual-probe.mjs scripts/test-qt-visual-driver.mjs
```

测试覆盖固定模型来源与摘要、下载大小限制和失败清理、TLS 降级拒绝、目录联接拒绝、区域越界、原图摘要、坐标回填、原矩阵不变、超时和取消终止、未知响应编号、输出限制、空闲释放与进程所有者退出，以及重识别的身份和像素绑定；不会读取当前桌面或发送消息。

## 动态布局候选

`scripts/locate-wechat-layout.py` 使用同一隔离 OCR 环境处理项目原生捕获的全客户区图片，不依赖 Codex。当前适配微信 4.1.15.56 深色界面，按长分隔线、完整圆角编辑框、实际搜索/发送按钮轮廓与局部 OCR、录音图标多尺度模板定位。窗口宽高分别变化时重新检测这些锚点，不把旧坐标整体缩放。输出包含原图摘要、尺寸、DPI、区域和证据，不包含聊天正文。不能识别的版本、主题、遮挡、重复锚点或低置信度返回明确失败。

主模式只提供布局候选，`--recording-state` 独立识别录音取消/发送控件并拒绝角色反转；`--contact-panel` 要求真实侧栏边界、五个固定操作标签、唯一成员头像及添加控件的相对关系，关闭锚点来自真实标题文字框。模板文件只保存录音控件和公共导航图标的裁剪像素，不含账号、头像或消息。本人头像仅通过当前截图中的唯一几何连通块寻找，标题 OCR 只返回位置与分数。

窄窗口中的搜索占位标签或标题若已经读出唯一、完整且在控件内的一行文字，仅置信度不足时，可对同一局部像素固定放大 1.25 倍，以 cubic 插值重识别一次。搜索必须仍为完整固定标签；标题前后全文必须完全一致，不能用另一串文字替换。重识别保留原始置信度、原图摘要和区域绑定，坐标映回原像素，最终仍要求每个字符至少 0.97；不修改源图片，不对错误、重复或越界文字试探多个比例。标题仅用于导航触发，完整联系人身份仍由独立资料证明核验。

96 DPI 的搜索标签主路径使用固定上下各 16 像素的边缘复制上下文，解决小字号检测不到文字的问题。该处理在识别前按 DPI 固定选择，不按预期文字或得分挑选变换；它不读取相邻聊天区域、不修改原图或置信度。识别框映回原区域，落在虚拟填充中的字符直接拒绝；仍须是完整唯一的固定标签、达到 0.97 并位于真实控件内，不再追加放大重试。

布局分析的最小宽度与原生接口统一为 600 像素，允许分析不代表接受布局。96 DPI 的编辑框三条内沿从已经识别的框线窄带中独立测量：只接受方向正确、至少 95% 长边支撑、最多两个连续像素的抗锯齿梯度。完整内容区一直覆盖到实际工具栏顶部；JS 会重验内沿证据、有限偏移和全区域像素，不允许裁一块空白来绕过草稿检查。真实 616×590、96 DPI 截图已离线通过八项布局证据与完整空编辑区检查，600 像素合成边界及边缘内容拒绝测试通过；这些结果不代替该尺寸下的现场输入或发送验收。

完整编辑区的圆角像素不会从摘要中删去。除已有的 0/1 像素顶部相位外，另支持实际 776×728、120 DPI 截图中出现的有限两轴相位：前三行的外侧空隙必须严格为 2→1→0，连续圆弧的内侧范围逐行收缩。仅该相位多检查一行一列，并要求左右两个完整二值圆弧各自转置对称、对应行内沿相差不超过一像素；普通相位保持原检查范围。颜色、全编辑区像素和光标检查不变，光标候选只影响另一份完整摘要中的光标区域。孔洞、跳相、延迟相位、非对称、额外边缘像素、文字和附件仍拒绝。七档已支持 DPI 的左、右及双侧组合离线测试通过，仍不将视觉候选当作空草稿授权。

导航长边仍优先使用原灰度规则。仅在没有灰度候选时，可核验原始 RGB 暗色台阶：至少一个通道差达到 4 的长边支撑须达 95%，两侧近中性暗色且三通道同向至少相差 3 的支撑须超过 78%，并且只有一个单像素候选。这样保留了灰度转换前的颜色证据，不把灰度阈值直接降到 3；短边、彩色单通道变化、多个候选和多像素梯度拒绝，已有多个灰度候选时也不尝试替代路径。真实 1920×1080 桌面中的 770×734、120 DPI 截图已离线通过此定位与完整编辑区检查；资料身份和实际发送仍需各自验证。

同版微信在小窗口中可能把导航背景绘成连续渐变，没有可测量的分界台阶。仅在主窗模式的灰度与 RGB 路径都没有候选时，可使用三个公共导航图标联合定位：联系人、盒形和指南针图标各自必须唯一，相关分数至少 0.93、与其它候选分差至少 0.10，且三者的同列、顺序、间距和 DPI 尺度关系一致。本人头像必须独立识别并与图标同列；搜索框和聊天长边仍独立检测，所有八项布局证据及完整编辑区检查保持不变。已有歧义边界不会转入该路径。资料侧栏和 Python 录音态模式尚未执行这套完整交叉检查，没有长边时明确拒绝，不继承主窗证明；正式语音的原生自适应流程不受此限制影响。`wechat-navigation-templates.json` 仅保存 96/120 DPI 原生绘制的两组三种公共图标，包含匿名来源图摘要与裁剪矩形，整体和单图摘要固定；两个样本组共同参与唯一性检查，任一组发现第二处候选仍拒绝。125% 的原生栅格与 100% 图标放大结果不同，因此使用独立的公共图标样本，不降低相关分数或分差门槛；准备组件时也校验整体摘要，源码导出保留该文件的原始字节。真实 612×585、96 DPI 和 776×728、120 DPI 保存截图已离线通过布局识别、完整编辑区及 JavaScript 证据协议；缺失、重复、错序、位移、不同尺度和虚假渐变反例均拒绝。合成 DPI 测试不代表这些 DPI 的现场图标已经全部实测。

所有模式均声明 `emptyDraftAuthorized:false`、`identityVerified:false`，不会生成空草稿证明或联系人身份授权。调用方还须绑定原生进程/尺寸、重采像素、检查完整编辑内容区、核对完整联系人身份，并在每次输入前完成现有活动与授权检查。候选定位成功不代表已发送，也不代表任意 DPI 或所有微信版本实测完成。

原生语音另支持 `recordingUi.adaptive`：窗口版本与正常录音入口已核对后，只用当前编辑框底部作为搜索范围，录音开始并出现本微信进程的活动音频会话后，使用编译时嵌入、整体摘要固定的取消/发送角色模板做多尺度匹配。两个角色必须唯一、取消在左且发送在右、间距与高度关系合理；重新检查前台、活动版本、窗口归属和区域像素后才固定为本次录音的完整 RGBA 摘要，后续继续使用原来的精确像素校验。模板包含已观察到的 120/144 DPI 控件，不从未知录音画面学习新模板。匹配失败不盲点取消或发送，保留录音状态未知的阻止标记。这个流程不替代空草稿、目标身份、账号、实际音频会话或活动守卫，也不代表录音内容已经送达。

`node --test scripts/test-wechat-layout.mjs` 覆盖合成宽度单独变化、高度单独变化、同时变化、分辨率与 DPI、录音角色、侧栏歧义、固定像素变换及错误图片摘要。真实离线截图已验证 1100×800@120、1080×1101@144、931×978@144、931×888@144 主窗口，以及旧 120 DPI 录音界面和新 144 DPI 联系人侧栏；动态现场发送仍以独立实机验收为准。
