# Qt 微信本地界面发送适配

`scripts/qt-visual-driver.mjs` 和 `scripts/native-ui/WechatQtActions.cs` 在 DSH 自带 Node 与 Windows .NET Framework 上运行，不依赖 Codex 的截图或键鼠接口。

界面发送模式只连接已经运行的微信，不启动、重启或退出微信。窗口暂时不可见、最小化或候选不唯一时，本次界面操作会停止；这些情况不证明账号退出登录。请先检查现有窗口，不要通过重复启动微信处理窗口定位失败。

## 已实现的边界

- `prepare(job)` 核对账号进程与数据库并搜索联系人。共享自适应模式的私聊搜索优先使用公开微信号；没有公开微信号时，只使用当前数据库中唯一映射到该联系人的备注或昵称。内部稳定 ID 继续用于对象选择、授权和回执，不直接把内部 wxid 当作可搜索微信号。清空搜索框并粘贴，随后按一次专用 Return；不读回查询，不打开资料页，编辑区就绪后也不读取草稿或检查空白。普通模式继续核对自身、私聊搜索行及好友资料，并读取草稿。此阶段会操作界面。备注／昵称回退已在一条真实私聊回复中取得唯一数据库回执，含导航连续前台占用为 1,375 毫秒；该单例不保证所有联系人或一秒以内；不增加界面身份核验或查询、正文读回。
- `observe(job)` 仅检查当前窗口、像素与用户活动，不注入输入。
- `typeGrapheme(job, guard)` 在普通模式每次模拟输入一个完整字符并读取草稿核对；共享模式使用快速粘贴并恢复剪贴板，不复制正文读回。未得到明确完成结果时保留不确定状态，不重复输入。
- `submit(job, guard, { canSubmit })` 在仍有效的账号事务中复核发送授权。共享模式消费本次原生粘贴动作签发的一次性证明，只按一次专用 Return，不把该证明称为正文核验；普通模式核对完整草稿后只点击一次发送。没有点击回退，发送结果由本地 Reader 的回执确认。
- `prepareVoiceSession(job)` 为本次目标生成短期语音会话。共享模式显式使用 `draftPolicy:'unchecked',emptyDraftConfirmed:false`；普通模式继续要求已核实的私聊和空草稿。Qt 输入进程正常退出、输入互斥锁释放后才允许独立语音进程接手。

共享搜索 Return 后的呈现等待不增加 OCR、资料页或正文读取。标题改变时，要求新的主窗标题／编辑区两帧稳定且间隔至少 35 毫秒；标题不变时先等待至少 350 毫秒，再采集两帧。见过新标题后，不允许旧标题重新作为切换完成依据；总计最多 600 毫秒、18 次观察。此规则处理正常页面呈现，不是另一份联系人身份核验，350 毫秒也不能保证任意迟延的切换已经结束。

共享文字成功提交后，同一驱动可保留一次、最长 30 秒的联系人导航记录。下一条仍为同账号、同对象，且窗口、位置尺寸、DPI、活动代际和新截图标题均一致时，直接聚焦编辑区，省去重复搜索；任一条件变化、失败或打断即消耗记录并恢复正常搜索。记录不含正文、草稿或提交凭据，群聊仍读取当前联系人目录；它不跳过新消息的粘贴、发送授权和数据库回执。2026-10-30 独立手动双消息验收中，第一条含搜索为 1,047 毫秒，第二条同聊天复用为 485 毫秒，两条均有唯一真实数据库回执且各借还焦点一次，见 `manual-focus-receipt-audit-20261030-1793327011337.json`。这是手动测试数据，不替代正式模型自动回复的 1,032–1,282 毫秒样本。

同一次同步发送授权内部共享一次设置读取；返回、异常或异步等待后立即失效。名单、控制状态、权限结果及提交意图不缓存，异步准备后仍重新读取设置。最新四文件提速差量经 353 项相关检查、612 文件隐私扫描及源码／生产配置前后哈希检查通过，证据为 `post-full-performance-validation-1793324567000-summary.json`；这不是再次全仓回归。

账号核验的原生拒绝结果仅透传严格结构和白名单匹配的原因代码，不输出原始路径或错误正文。只有在账号检查明确尚未借用焦点、未输入、无语音租约及无待清理界面操作时，拒绝会持久暂停发送并保持 Reader 运行，等待手动恢复；未知异常、取消、焦点已借用或清理不明仍保留原错误边界。最后六文件修复经 416 项相关检查、隐私检查与稳定哈希验证，见 `final-account-pause-validation-1793326878773-summary.json`。旧一次失败的原生原因已被旧包装层丢弃，后续只读核验成功不证明旧失败的具体原因。

共享模式的文字与搜索粘贴均显式请求 `readback:false`；返回 `pasteApplied:true,readbackPerformed:false,intendedText`，保留真实的操作后区域和一次性步骤证明，不返回 `pasteVerified`。这不会检查已有正文或附件，也不在人工打断后重新比较正文。普通模式的受控草稿读取继续保留以下模板、复制和鼠标停靠规则。

配置了独立鼠标停靠区 `pointerParkRect` 时（兼容旧的 `focusActivateRect`），读取草稿前用新鲜区域截图、窗口绑定、空闲与按键检查，执行一次纯鼠标移动，使指针离开编辑区；此位置不授予焦点激活权限，不点击标题栏，仍核对编辑器焦点保持。普通模式空草稿的完整模板和 650 毫秒观察期限不变。共享焦点租约记录最初鼠标位置与最后一次自身输入的实际落点，只有用户活动版本未变、鼠标仍精确停在该落点、没有按键且原窗口仍有效时才归还；用户移动后绝不覆盖。语音交接前先结束 Qt 的鼠标占用，再用完整校验的最终 Windows 输入时间戳绑定后续录音会话。

普通模式初次空草稿检查在完整复制观察结束、剪贴板序列未变化后，先比较整个编辑框像素；若只有一个符合严格颜色、位置和尺寸限制的实心光标，可以将它还原为背景色，再要求整个编辑框精确匹配已有空模板。其他任何像素差异仍不通过，不学习新模板，也不修改原截图。2026-10-28 同一窗口的无发送实测中，这使 `readDraft` 从 1330 毫秒降至 813 毫秒，复制观察仍为 656 毫秒；这是历史草稿读取耗时，不含联系人切换，当前共享模式不执行此步骤。

普通模式的资料页必须在精确的区域显示带“微信号”或“WeChat ID”标签的完整 ASCII 微信号，可支持窄区域内相邻两行的明确换行。OCR 结果须与本地联系人库的别名或内部微信号唯一对应；同时检查两个字段之间的冲突。未设置个人微信号时，自身资料显示的内部微信号须与 Reader 账号及进程数据库证据相符。昵称、备注和聊天标题本身不作为身份依据。截图同时验证前台、进程路径与创建时间、会话、窗口尺寸、DPI、遮挡和真实键鼠活动；每次输入前重新验证。

## 本机标定

配置放在 `state/ui-runtime/qt-visual.json`，不随源码迁移。使用 `validateQtConfig()` 验证后再启用。主要字段：

- `version: 1`、`backend: "qt-visual"`。
- `executable`、`executableVersion`、`executableSha256`；微信升级后必须重新标定。
- `hwnd` 可为 `"auto"`；普通模式只绑定前台且程序路径匹配的微信窗口。共享电脑模式另有经过空闲、身份与布局校验的焦点交接。
- 当前 Reader 的 `account`、`accountRef`、资料页 `accountAlias`。
- `idleMs` 至少 1000；`ocrBackend` 为 `rapidocr` 或 `windows`。
- `layout.width/height/dpi` 与原始客户区一致；所有矩形使用原始像素、相对客户区的 `left/top/right/bottom`。
- `layout` 的矩形字段：`header`、`search`、`firstResult`、`searchResultIdentity`、`profileOpen`、`profileAlias`、`profileClose`、`selfOpen`、`selfAlias`、`selfClose`、`editor`、`send`。普通模式联系人导航必须标定 `searchResultIdentity`，完整包含私聊分类、昵称和带标签的完整微信号；`firstResult` 的整个点击矩形必须位于该身份区域内，不能只核对中心点。
- 共享模式可选 `layout.focusActivateRect` 和 `layout.focusActivateRgbaSha256`，必须成对。矩形是人工确认的空白标题栏区域：客户区顶部 48 像素内，宽 20–200、高 8–40，左右各避开 160 像素；hash 为该完整区域逐行 RGBA 像素指纹。必须采集**非前台**微信的模板，不能拿活动标题栏底色代用。`qt-calibrate.mjs --focus-plan <绝对JSON路径> --save [--replace]` 的计划仅含 `{ "rect": { "left": …, "top": …, "right": …, "bottom": … } }`；操作者将其他应用留在前台，同时露出微信该区域。`captureQtFocusCalibration` 通过只读 `inspectFocusActivation` 核对原进程、桌面、布局、活动与区域可见性、两帧稳定像素，并核验当前账号后保存；不会 raise、激活、点击或自动学习。普通前台布局校准不接受这个字段。当前只接受一个精确模板。
- 微信需先开聊天信息面板再点头像时，增加 `layout.profileMember`、`layout.profilePanelClose`；资料卡可用 `profileCloseKey: "Escape"`、`selfCloseKey: "Escape"` 关闭，对应的关闭矩形便可省略。点击后的等待由 `settleMs` 控制，默认 400 毫秒。
- `layout.emptyEditorSha256` 是**整个空编辑区**逐行 RGBA 像素的 SHA-256（Alpha 固定为 255，与语音模板一致）。只看上去空白或 OCR 没读到字均不够。
- 可选 `layout.emptyEditorSha256s` 保存同一布局、DPI、主题与微信版本下，经过操作者确认的完整空编辑区模板，用于光标或占位提示的不同状态。数组内不得重复，和必需的 `emptyEditorSha256` 合并后最多四个模板。运行时在复制未改变剪贴板的前提下，最多等待 650 毫秒匹配其中一个**完整**像素指纹；仅允许按上述严格规则归一化唯一光标，每次采样前后仍检查焦点、窗口、用户活动和剪贴板。不忽略其他区域、不使用相似度或自动学习。此可选列表目前需按确认后的截图手动配置；重新标定主模板或改变布局后，必须重新确认各个模板，不可沿用其他环境的 hash。
- 若资料页是独立窗口，可指定 `profileSurface` / `selfSurface`，包含 `width`、`height`、`alias` 与 `close` 矩形。未配置下述精确弹窗标定时，仍只接受同进程且 owner 链归属于原微信窗口的弹窗。
- 多行输入需显式标定 `newlineKey: "Shift+Enter"`，未标定时拒绝换行，避免误发送。
- 语音另需 `voice.recordStartRect`、`voice.mouseParkRect`、`voice.recordingUi`。`recordingUi` 包含 `focusHwnd`（同窗口时可写 `"same"`）与 `cancel/submit` 的 `{ rect, rgbaSha256 }`。

启动适配器必须显式传 `enableInput: true`；默认只读。`allowSubmit` 与输入开关分开，并要求回执提供器。

可用 `qt-calibrate.mjs --plan <绝对布局JSON路径> --save` 生成本机配置；已存在时需显式 `--replace`。布局方案只提供上述矩形、可选 OCR/等待设置和资料微信号；账号、窗口句柄、进程、版本、尺寸、DPI 和空编辑区像素指纹由本机读取。程序仅截图并验证进程账号，既不复制草稿也不操作微信，因此生成配置仍不会把“空草稿已验证”或“已可自动发送”设为真。运行时另做完整检查。API `captureQtCalibration({ root, plan, save })` 返回完整配置和本地图片位置，CLI 只打印匿名状态及文件位置。

显式保存标定时，原配置和新配置会按账号引用、微信程序路径/版本/SHA-256、客户区宽高和 DPI 存入本机 `state/ui-runtime/qt-layout-profiles`。界面服务在每次准备发送前只读检查真实窗口布局；回到已有的完全相同布局时自动选用对应配置，不要求重新标定，也不以显示器分辨率代替微信窗口尺寸。窗口在同 DPI 屏幕间仅移动位置，不改变这些客户区坐标。旧 `qt-visual.json` 仍可作为唯一当前配置使用。

布局变化时若有待续草稿、待确认输入或正在持有前台租约，不切换执行器。没有精确配置时，正式服务会调用 `qt-auto-layout.mjs` 的本地自动定位流程；当前仅适配微信 4.1.15.56 暗色界面、DPI 96–240。它通过真实分隔线、编辑框轮廓、头像、标题、搜索和发送控件识别新的宽高与缩放，不能按比例缩放旧坐标。定位使用项目自身 OCR Python 环境，不依赖 Codex。

共享电脑短暂切换模式遇到新尺寸或 DPI，且首次只读取图因遮挡失败时，自动调用 `captureLayoutRaised`：按当前窗口身份和几何，以 `SWP_NOACTIVATE` 临时置顶微信，连续采集两张完整位图，随后撤销临时置顶。在原前台、用户活动及窗口身份仍一致时，把微信放回原先位于它上方的可见普通窗口后方；不抬起或下移其他应用。全程不请求键盘焦点，不点击、不输入、不访问剪贴板；图片编码、OCR 和两帧控件锚点校验均在恢复后执行。支持的场景不要求手动把微信调到前台或保存新布局；新候选只在内存使用，不按旧尺寸换算坐标。此步骤仅解决自动定位取图，后续文字、联系人导航和语音操作仍沿用原有焦点交接。

取图前要求原前台窗口与微信属于不同进程、原本位于微信上方，微信客户区完整处于显示范围内，并满足空闲与按键释放条件。当前路径只接受微信主窗及其附属窗口原本均非置顶；不移动或缩放窗口。异步请求必须实际观察到置顶生效及撤销，才确认恢复。用户活动、焦点或窗口状态变化会中止取图，仍撤销本次临时置顶，但不再重排用户新选择的窗口；原窗口消失或恢复未知时不宣称完整恢复。普通只读遮挡可在队列退避后重试；尝试显示后仍被遮挡且恢复已确认时，暂停发送并保留 Reader 运行，不反复调窗。

资料弹窗因 `QT_POPUP_NOT_OWNED` 暂停时，可在成功捕获过主窗的同一个 `QtActionsClient` 中调用 `request('inspectPopup', {hitRects:[config.layout.selfOpen,config.layout.selfAlias]})`。该只读诊断保留原主窗绑定，列出前台窗口、`GW_OWNER` 链、同 PID 可见窗口、线程的 active/focus 句柄及矩形中心的原生命中，不切换焦点、不复制内容、不读取窗口标题或正文。`stableObservation:false` 表示采样期间身份、前台或用户活动发生变化；即便为 true，这也只是诊断快照，`authorizationGranted` 始终为 false。`WindowFromPoint` 不返回隐藏或禁用窗口，命中也不能证明资料归属。同 PID、同类名和邻近位置均不会绕过原有 owner 链、进程创建时间及账号微信号验证。依据：[GetWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindow)、[GetAncestor](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getancestor)、[WindowFromPoint](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-windowfrompoint)、[GetGUIThreadInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getguithreadinfo)。

### 动作触发的精确 Qt 弹窗标定

部分 Qt 资料卡没有 Win32 owner 链，搜索浮层也可能是同线程独立窗口。可选 `selfSurface.popupCalibration`、`profileSurface.popupCalibration` 和 `searchPopupCalibration` 已接入，本机已采集并验证自身资料、搜索及联系人资料的导航。其他机器必须独立标定，配置不会凭同 PID 自动启用此路径。`inspectPopup` 另返回每个窗口的 `clientRect`、`clientScreenRect` 和 DPI，供本机采集；不能直接把某个同 PID 窗口当成资料卡。

每项标定包含十个基础字段：`version:1`，`kind`（`profile` 或 `search`），精确 `className`，`ownerRelation`（`root-owned` 或 `same-thread-unowned`），`ownerDepth`，相对主窗客户区原点的 `windowRect`，`clientWidth`、`clientHeight`、`style`、`extendedStyle`。有 owner 链时深度为 1–16；无 owner 时深度必须为 0。资料卡客户区尺寸必须与相应 surface 一致。搜索浮层可额外标定 `heightVariants`（最多四个不同高度）或 `heightRange: { min, max }`，二者不能同时存在；只有高度可在明确边界内变化，原点、宽度、HWND、线程、类名、样式和其余身份仍固定。所有用于结果检查和点击的区域须位于对应已验证表面内。标定与原配置的可执行文件指纹、主窗尺寸及 DPI 一同失效，不使用默认类名或猜测矩形。

绑定仅由本次受保护的“自身头像点击”“Ctrl+F”或“最终联系人头像点击”触发：点击区域也须属于本次已捕获的像素锚点。触发前记录可见窗口集合，10 秒内只接受唯一新出现的窗口；它须与主窗有相同 PID、进程创建时间、程序路径、GUI 线程及 DPI，并与标定的 owner 关系、窗口矩形、客户区尺寸、类名、样式相符，搜索高度只按上述显式范围处理。相隔 35 毫秒的两次检查都必须唯一匹配同一 HWND。之后固定该 HWND，每次观察和输入都重查，不能跟随任意同进程弹窗。资料卡必须位于前台；当前搜索路径仅支持主窗保持前台、搜索浮层不夺取键盘焦点的形式。其他焦点形式或未标定的几何变化需先采样再适配，不能默默放宽。

搜索时遮挡检查只豁免这一个已绑定且仍精确匹配的弹窗；点击它还需同时落在已捕获锚点和标定弹窗内。其他窗口仍阻止输入。弹窗绑定仅证明本次界面操作的连续性。普通模式继续完成资料页完整微信号 OCR；共享自适应模式优先使用公开微信号；没有公开微信号时，只使用当前数据库中唯一映射到该联系人的备注或昵称搜索，并按一次专用 Return，不再打开联系人资料或重开搜索。两种模式均保留账号数据库与唯一联系人映射。缺少标定、窗口早已可见、出现多个候选、未标定的位置/样式变化或用户活动都不能建立新绑定。离线测试覆盖配置拒绝、触发动作、返回证据和身份核验；历史普通模式的本机完整联系人准备已通过自身账号、私聊搜索行完整 ID、打开后资料、空草稿和最终焦点归还核验，返回 `ready:true`，期间没有向该好友发送消息。这不等于该联系人已完成自动发送验收。

## 2026-10-26 后台录音能力验证

本机微信 4.1.15.56 的文件传输助手完成了独立于生产执行器的界面实验：开始原生语音录音后，将前台切到控制面板，并在其搜索框输入测试文字。约 30 秒的后台阶段中，两次只读音频会话查询均确认同一微信进程在 CABLE Output 上保持 active、singleProcess 的捕获会话；返回微信后仍显示录音倒计时。随后点击取消，录音界面消失，会话变为 inactive。没有点击发送，也没有播放音频样本；此实验不能证明接收端音质或后台发送成功。

测试前、聊天界面和录音界面的可访问控件树均仅暴露外层窗口与两个绘图区域，未取得可直接调用的开始、取消或发送按钮。开始和取消仍通过前台坐标点击完成。Win32 定向消息、离屏捕获、最小化、锁屏及双屏均未在本次实验中验证，不能据此宣称它们可用或不可用。

输入框左侧的麦克风是语音输入入口，与发送按钮旁的原生语音消息入口不同。前一次语音输入的失焦停止结果不作为原生语音消息的证据；正式结论仅使用 `background-voice-native-*` 记录。

临时录音路由的三个默认角色均切到 CABLE Output 后才进入测试，结束后逐项核对已恢复原来的 UGREEN Camera Audio；三个默认播放角色保持不变。本机音频会话与路由记录保存在忽略的 `state/diagnostics/background-voice-*.json`，不含录音样本。

这一结果证明微信自身能够在失去前台焦点时继续原生录音。默认执行器仍保留用户活动、前台、身份和像素校验；它的失焦暂停是实现的保护条件，不能作为微信后台录音不可行的结论。副屏能够增加可见空间，但不隔离同一 Windows 桌面的键鼠输入与焦点。

## 单屏语音交接与快速粘贴（实验）

前台占用现在按每次连续借用分别记录：从请求激活微信前开始，到确认归还焦点并完成该段指针归还后结束。同一段内实际执行的联系人定位、切换、界面准备和录音开始都计入，不能只截取录音按钮的阶段。只有确实归还焦点才拆成下一段；后台录音及获得焦点前的空闲等待不计入。控制台显示各段和最长单段，不用多次占用的累计值代替一次打断。匿名测量保存在 `state/foreground-timing/latest-text.json` 与 `latest-voice.json`；缺少开始边界、归还未确认或旧报告没有该字段时明确显示未取得完整区间，测量本身不改变发送权限、回执或重试策略。

控制台的“共享电脑短暂切换”统一控制快速文字和语音焦点交接，仍独立于“操作保护”。开启后语音计划使用 `focus-handoff`，默认仍为 `foreground`；副机部署方案保留。开始录音前保存原前台窗口的 HWND、PID 与进程创建时间，确认录音后返回该窗口。提交前重新记录此时用户正在使用的窗口，等待按键与鼠标按钮释放、短暂无操作，再切回微信检查原聊天及录音状态；提交后返回第二次记录的窗口。用户主动切走时不强制抢回。后台录音仅检查进程、窗口、桌面与音频会话，不使用被其他窗口遮挡的屏幕像素证明聊天身份。

当前原生交接仍有必须明确的限制：提交前安全间隙最多等待 1.5 秒；共享模式已有规则允许用户在其他应用内正常操作，不因此逐次取消。真正影响录音的人工活动或返回微信会停止播放。只有原录音已绑定、尚未尝试提交、原窗口与采集会话仍有效，且在期限内可以重新取焦点时，才用一次 Esc 取消。仅在明确确认 Esc 已应用、录音结束、未尝试发送和屏障解除后，生产队列才保存旧尝试，以新 ID 等待空闲后重录同一段；旧 ID 不再录制。原窗口关闭、音频或布局变化、取消结果未知仍保留屏障，不能据取消意图重录。自动交接仍标为实验；上述测试当时未启用本机自动回复。Esc 取消已通过上述“外部激活现有微信”的受控单例，另一次新 ID 录制也已确认；自动队列自行重录与其他打断方式仍待现场覆盖。计时报告的 `initialForegroundElapsedMs` 仅包含原生录音阶段，不含 Qt 的联系人定位与准备，不能当作整条回复占用焦点的总时间。

快速粘贴由共享电脑开关派生，不再作为单独选项；关闭共享时继续逐字输入，开启时用于界面文字正文与联系人搜索。发送队列在粘贴前持久化整段意图，原生确认粘贴已执行且剪贴板恢复后推进，不复制正文读回；未知结果不得重贴。剪贴板使用完整格式备份与恢复，遇到无法备份的格式或用户复制了新内容时暂停。共享模式仍保留账号、目标绑定和提交授权，明确跳过空草稿与正文核验；搜索和文字提交各按一次专用 Return。语音发送仍点击按钮，取消使用 Esc。新路线的现场结果以显示验收矩阵为准。

同一聊天只有在原有进程、输入监测代次、用户活动版本、标题像素等验证均连续有效时才复用导航；已粘贴文字的步骤续接另按上文的任务绑定处理。共享自适应模式首次切到新私聊优先使用公开微信号；没有公开微信号时，只使用当前数据库中唯一映射到该联系人的备注或昵称搜索；内部稳定 ID 继续用于选择、授权和回执，不增加界面身份核验。群聊按完整群 ID 授权，使用新读取的唯一群名搜索；同名群或与联系人搜索名冲突时停止。这两条共享路径不读回查询，也不额外打开资料页。切换后保留编辑器就绪检查，它不等于第二次联系人身份复核。普通模式仍核对资料页。最终文件传输助手 V2 已在同一连续前台区间记录联系人导航与开始录音；更早独立分段记录没有包含导航。跨用户活动续接、跨显示器布局，以及有人持续使用电脑时的新自动流程仍须按当前版本验收。

共享语音在进入发送意图前先做只读空闲检查：检测到用户活动、按键未释放或缺少可返回窗口时保留排队状态，不开始录音。进入实际准备后发生干预仍保守停止。完整导航纳入独立的总预算；开始录音前必须同时为原生执行、清理和回执预留至少 20 秒，预算不足会在录音前结束。模式修改对下一段语音生效；关闭发送许可、暂停任务或撤销收件人仍会取消当前工作。

普通模式的 RapidOCR small 与 medium 模型在文字或语音获取焦点前预热，后续同一进程复用本地模型；预热不截图、不访问窗口、不联网。模型初始化失败或取消会在切换焦点前停止。首次身份识别使用完整图，完整微信号的置信度门槛保持不变。备用 medium 识别仅处理已经标定的完整搜索结果区域，仍包含私聊分类、姓名与完整微信号，不读取搜索输入框作为身份依据。

首次联系人导航先在后台查询本次目标的数据库资料，并传递取消信号；查询结果只包含本次私聊的公开微信号、缺少公开微信号时经当前数据库证明唯一的备注／昵称，或本次已绑定群聊的新鲜唯一群名；目标始终绑定内部稳定 ID，不跨账号或目标缓存。共享自适应模式不预热联系人 OCR，取得焦点后保留当前进程/账号证据、完整查询粘贴、一次专用 Return 和主窗口编辑器就绪，不读回查询或草稿。普通模式查询与 OCR 预热并行，并保留自身资料、精确私聊搜索行和联系人资料核对。原聊天连续验证仍有效时不重复查询。

共享语音新增一次性原生进程的两阶段协议 `--private-warm`。第一阶段只安装并持续运行活动监测，待消息泵开始后返回带 nonce/monitorId 的 ready；此时不取得输入或音频互斥锁，不访问微信、音频设备，不点击或录音。父端在 Qt 完成本次目标与界面准备并退出后（共享模式不读取草稿），提交同一 nonce/monitorId 绑定的完整新鲜执行请求。只有一次有效提交可以进入执行阶段；这时才取得互斥锁，保留完整 `idleMs`、lastInputTick、按键释放、窗口/聊天/音频等原检查。预热阶段的真实活动更新监测版本和最后活动时间，执行阶段恢复原有取消规则。预热最多 60 秒，执行仍最多 18 秒；父进程关闭或取消会终止进程。这样可让完整的活动观察时间与导航重叠，而不是减少保护窗口。普通 foreground 路径保留原启动方式；未知的执行结果不得换入口重发。该版本已完成上述文件传输助手实机验收，协议与生命周期的取消分支仍以离线测试为主要证据。

原生语音为开始录音和提交分别记录鼠标原位置；第二次记录取提交前的当前位置，不沿用第一次原位置。每次确认归还焦点后，只有原窗口身份、虚拟桌面范围、活动版本和按键状态仍有效，且指针精确停在程序最后一次自身输入的位置时，才执行一次纯鼠标移动归还。独立的输入版本也记录后台与归还阶段的真实活动，用户已经接管时跳过归还，不把鼠标拉回旧位置。报告仅增加 `initialPointerRestored`、`finalPointerRestored`、`pointerRestoreSkipped` 三个布尔值，不保存坐标；跳过鼠标归还不覆盖已经确认的发送回执。

搜索结果原识别仅因置信度不足而未通过时，允许用固定 medium 模型对同一原图的 `searchResultIdentity` 区域重识别一次，不做像素转换。原识别必须已经读出同一完整微信号、正确私聊分类与三行结构；重识别仍须通过全部原阈值和结构检查，并核对原图 hash、原尺寸、精确裁剪区域与模型标识。坐标回映到原始截图，点击前再次检查完整区域像素不变。错误身份、群聊分类、改动像素或再次低置信度都停止，不重复识别或点击。识别参数不包含预期微信号，返回置信度不作人工修改。本机三个实际失败样本的完整 ID 最低置信度均达到 0.99978，区域 medium 耗时约 2.8 秒；此前成功样本仍只走原始 small 识别。此离线结果不能替代完整导航的实机验收。

自动交接先请求一次 `SetForegroundWindow`，随后最多等待 500 毫秒确认。系统拒绝且配置了上述模板时，才使用普通鼠标后备：异步调整到非置顶窗口前部，保留位置、尺寸和原前台；再次核对桌面、进程、几何、活动和按键，再要求标题栏像素连续两次匹配且原生命中属于该微信窗口，最后只点击一次。未发生用户干预且指针仍处于程序点击点时才归还指针。语音第二次取焦点沿用同一校准模板。归还其他应用仅请求并确认 `SetForegroundWindow`，没有标定的其他应用不会被猜测点击。此流程没有 `AttachThreadInput`、内存注入、全局快捷键或输入阻塞；微软说明附加输入队列后的前台请求可能同步挂起，因此不使用该路径。依据：[微软对附加输入队列的说明](https://devblogs.microsoft.com/oldnewthing/20080801-00/?p=21393/)、[SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos)。模板缺失保留原单次前台请求，模板不匹配则停止；本机非前台模板的获取焦点及归还已实测通过，其他布局仍需单独验证。
