# 微信 UIA 控件模式

普通文件可从已启用文件收发的助手聊天发送。2026-11-16 在微信 4.1.15.56 的文件传输助手验证了一份生成的 PDF。微信消费了原始文件剪贴板格式并显示内联附件，数据库返回匹配文件名、大小、MD5 和服务器消息 ID 的文件记录。该次前台占用 250 毫秒，剪贴板和焦点均已归还。记录见本机 `state/diagnostics/uia-file-pdf-nov16pdf6.json`。另有独立文件确认窗口的处理逻辑，本次实测走的是内联附件。

UIA 模式是针对微信 **4.1.15.56 x64** 的独立控件执行路径：后台读取真实控件，对需要前台的操作短暂借用微信焦点并归还；与 OCR 模式共用队列和数据库回执。原生语音目前在开始录音后归还焦点，录制和提交均在后台完成，提交不再申请第二次前台。它保留用户活动保护、账号和聊天绑定，执行阶段不识屏。文字、静态图片、GIF 和原生语音均在本机文件传输助手完成受控发送与回执验收；这不代表任意联系人、所有窗口布局或长期连续运行均已验收。

当前控制台只有一个发送链路开关“UIA 快速模式”：开启走 UIA，关闭走 OCR 快速定位与焦点交接。旧共享电脑开关及其关闭后的长期前台分支不再作为运行选项。另有仅适用于 OCR 正文的“文字逐字输入”开关，默认关闭并快速粘贴，开启后模拟逐字输入；搜索词仍粘贴，图片、GIF 和语音不受影响。UIA 始终快速粘贴，此时逐字输入开关不可选但保留原选择。两条链路均保留操作保护、同一发送队列和数据库回执，具体对比见 [发送链路说明](SENDER_MODES_2026_10_31.md)。历史粘贴成绩可作为默认输入方式的参考，不是耗时保证；开启逐字输入后正文占用随字数增长，不能沿用粘贴成绩。本次模式整合保留现有 UIA gate，未删除或扩展其作用。

控制台在 UIA 模式下提供独立的“微信离屏”开关，默认关闭。开启后立即保存窗口状态并移到所有显示器之外，不等待下一条消息；关闭后立即恢复由该开关移动前的位置，UIA 模式继续运行。连续发送复用屏外位置，停止服务或关闭 UIA 时也会召回程序管理的窗口。已有未完成输入或录音时先处理该操作，避免中途移动；切换不解除发送队列的暂停。

离屏开关关闭时，UIA 使用微信的实际控件位置，不自动移动窗口。手动移到屏外的窗口也可发送；程序不会接管手动位置，关闭开关不擅自召回。若开启时窗口已手动放到屏外，保留原位置；关闭只解除开关选择。离屏减少遮挡和闪现，需要键盘输入的阶段仍会短暂借用真实焦点。服务停止时可以保存 UIA 和离屏设置。微信窗口与组件可用时，开启离屏会立即移窗。尚未打开微信或组件未准备好时，窗口将在下次启动机器人时移出。关闭离屏会先召回程序管理的窗口。

独立开关实机记录 `uia-offscreen-switch-result.json` 通过真实控制台 HTTP 接口验证即时移出／恢复，UIA 保持开启，原队列暂停文件未变化。`uia-manual-offscreen-uia1031manualoff1.json` 用外部放置模拟手动离屏：关闭托管移窗的发送实例连续发送两条文件传输助手文字，均有独立回执和焦点归还，发送结束后窗口仍保持外部放置的位置，最后由测试自身恢复。该记录不等于逐一验证任意部分出屏位置、显示器组合或 Windows 拖拽行为。

| 同聊天连续文字 | 140 毫秒 | 同上第二条 |

每项均确认屏外位置、独立数据库回执、焦点归还及退出后的原位置恢复。GIF 核对原文件 MD5；语音录制和提交在后台，接收音频内容与音色没有在本轮逐项比对。语音测试临时使用已安装的虚拟声卡输入，结束后已核对六个默认输入／输出角色均恢复到测试前设备，记录为 `uia-offscreen-audio-before.json`、`uia-offscreen-audio-restored.json`。

`WechatUiaOffscreenHost` 独立管理窗口位置，在实际移动或还原时短暂持有统一输入锁，停放期间释放。Qt 输入助手长期持有该锁，因此开关切换先确认发送端可安全停止、释放旧助手，再执行移窗并重新绑定；Reader 不重启。服务持有窗口管理器，已离屏的后续发送不替换助手。独立设置保存在 `state/runtime/uia-offscreen.json`，只读页面或 UIA 模式启动检查不移动窗口；服务启动时应用用户已保存的离屏选择。正式发送端不再按消息自动隐藏窗口。

普通前台 API 优先。若系统拒绝且目标确实位于所有屏幕之外，UIA 使用独立、限时的焦点助手；仅临时连接助手自身参与的输入线程，完成或退出后再检查真实焦点和用户活动。无需新增内存注入。搜索浮层采用单独的原生 UIA 能力：精确绑定主窗口、弹窗、线程、所有者、类别、样式、DPI、宽度和边框关系，两者都必须完全离屏。Qt 自行调整浮层位置和高度时读取实时位置，不再强制浮层处于主窗口矩形内，也不反复移动浮层与 Qt 布局竞争。实际输入继续绑定主窗口中的真实搜索控件；OCR 路径不使用该例外。纯 UIA 去除固定 35 毫秒浮层等待，并以 10 毫秒间隔在原有 600 毫秒预算内观察就绪状态，不重放搜索或正文输入。

正常关闭、输入管道断开会尝试还原；强制结束整组进程时保留持久恢复记录，服务下次启动先恢复窗口，再启动读取和发送，队列暂停或 UIA 已关闭也不跳过。`uia-offscreen-eof-result.json` 验证正常断开自动还原，`uia-offscreen-crash-recovery-result.json` 验证强制退出后启动恢复；二者均未发送消息、未改变前台。此前冷启动焦点拒绝和搜索浮层几何拒绝均保留失败记录，没有提交消息或重复发送原 ID。

最终跨模块回归 **700 项通过**，另有安装与源码导出 **8 项通过**。原生自测分别为 Qt **891 项**、语音 **318 项**、离屏宿主 **34 项**、隔离焦点助手 **13 项**；不同测试组不合计为独立总数。

正式文字发送继续使用短暂借用前台的 UIA 路径。新后台文字通道虽已完成代码接入，但新微信进程实测会在编辑器点击或字符输入时自行激活，因此 `allowBackgroundText` 默认关闭，正式服务不启用；仅显式诊断可打开，不能视为已可用的生产后台发送能力。

在“概览 → 电脑使用方式”选择“UIA 快速模式”。服务停止时可先保存选择，启动时核验组件、微信进程和控件。运行中切换会先结束当前发送通道，再核验实际微信进程和控件。尚未确认结束的发送或录音会阻止切换。完全未输入的排队任务可保留原 ID 和状态交给新通道，不能仅因队列非空就阻止切换；手动暂停状态也会保留，切换本身不会恢复发送。关闭后使用 OCR 快速链路，不恢复旧长期前台分支；旧“后台内存注入模式”的保存值不会自动变成 UIA 授权。

UIA 与 OCR 是同一开关的两种状态，不再同时显示互斥的共享电脑开关。UIA 仍对需要借用前台的操作执行焦点归还和用户活动保护。“微信离屏”是 UIA 的独立窗口摆放设置，继续保留，不作为第三种发送链路。

## 文字、图片和语音如何发送

| 类型 | UIA 提供的依据 | 执行与确认 |
| --- | --- | --- |
| 文字 | 搜索框、聊天编辑框、标题区域、发送按钮的实时位置 | 独立控件路径定位目标、粘贴并提交，按唯一数据库回执确认 |
| 图片 | 同一聊天编辑框与发送按钮 | 保留原图片导入、素材校验和图片回执流程；不要求另找“图片”按钮 |
| 原生语音 | 发送语音入口与录音工具栏 | 开始录音后归还焦点，后台播放录制并定向提交；按语音回执确认 |

完整控件发现安排在借用前台之前。文字、图片在输入和提交前快速复核编辑器、发送按钮和标题这 3 个角色；语音开始前再加语音入口、工具栏，共 5 个角色。控件路径只用于查找，仍核对运行时身份、类别、静态按钮标签、矩形以及同一窗口、进程创建时间、DPI、客户端尺寸和屏幕位置。缺少必要控件、有多个匹配或输入边界的布局已变化时暂停本次发送，不使用过期坐标，也不静默切换回旧识别路径。左侧“语音输入”是语音转文字，不能代替右侧“发语音”消息入口。

快速核验使用只读常驻进程，在后台完成进程启动和首次 UIA 调用预热。前台阶段仍读取当前控件，不把预热结果当作发送依据。本机两次核验的合计耗时从约 408 毫秒降至约 29 毫秒；这只是控件核验耗时，不是整条消息的前台时间。超时、取消或异常退出会拒绝当前操作；下一次后台准备确认旧进程退出后才重建，不重放已经输入的内容。服务停止和模式切换会回收该进程。

输入助手自身的首次 UIA 初始化和控件遍历也在借用前台之前执行。`warmUiaLocators` 只保存定位缓存，前后核对进程、窗口、线程、尺寸、DPI、前台及用户活动，不产生输入或发送许可；真正操作前仍重新读取控件。缓存提示按助手实例、窗口身份和几何绑定，助手替换或窗口移动后重新准备，同一实例连续发送不重复预热。语音在自己的首次焦点借用前执行同样的准备，图片和文字恢复流程不插入预热，避免破坏已有草稿的续接依据。

本机 `uia-filehelper-text-sequence-uia1031warm1.json` 连续两条文字均取得唯一数据库回执，归还焦点并释放草稿所有权。首条前台占用 **219 毫秒**，续发 **141 毫秒**；约 **105 毫秒**的首次初始化在后台完成，首次前台控件定位为 **9.9 毫秒**（此前样本为 95.2 毫秒）。这是当前聊天已匹配时的单次测量，不包含重新搜索，也不是任意负载下的固定保证。此次 Qt 原生自测 **862 项**、驱动与客户端测试 **335 项**通过；语音预热次序有离线测试，本次未重新发送语音。

独立 UIA 路径使用 `layoutMode:'uia-v1'`：先读取实时控件，再生成当前窗口的宽高、DPI、搜索框、标题、编辑框和发送按钮位置，不先运行旧像素布局解析器，也不要求自身资料入口或旧空编辑器截图模板。搜索弹窗只迁移同账号、同程序版本与摘要的身份信息，不迁移旧位置。布局发现不再预先检查标题栏备用点击区域，激活先调用 Windows 前台 API；直接成功时不读取或返回虚构的标题栏坐标，也不执行整窗遮挡、显示器覆盖检查。只有确实需要物理标题栏点击的备用激活路径，才重新定位并验证五点 `HTCAPTION` 命中，或五点 `HTCLIENT` 命中结合实时 UIA 标题栏结构、控件身份和几何排除。实际点击仍复核窗口归属、用户活动与焦点租约，但不读取局部画面，也不为标题栏重绘设置固定等待。备用物理点击遇到遮挡时仅按实际窗口归属作有界等待；旧 OCR 模式的画面校验独立保留。

Qt 根容器可能保留移动前的 UIA 矩形。根节点现按真实 HWND、PID、运行时身份和类别绑定，不将其容器矩形当作点击依据；Win32 客户区几何，以及实际搜索框、编辑器、标题和按钮的实时位置、所属父链与边界仍严格检查。这项调整只去除无关根矩形造成的拒绝，不授权使用过期的实际控件坐标。

对于数据库刚确认的唯一联系人显示名或群名，UIA 核验精确标题摘要、同一聊天页、可输入编辑器和搜索弹窗已关闭。当前会话已经匹配时直接定位编辑器；执行搜索后按当前控件状态作有界短轮询，不再固定等待 350 毫秒。显示名不唯一但具有数据库精确微信号映射的联系人，必须实际搜索该微信号，再核对数据库标题与本次搜索代际，不能仅凭当前同名标题走捷径。`prepare` 结束时不重复控件核验，实际输入与提交前的实时核验仍保留；失败或结果不明的输入不重试。

群公告等界面差异会改变聊天标题区高度。仅在本次搜索已成功、尚未输入正文时，允许刷新位置：六个角色的运行时身份、路径和类别均未改变时，局部读取实际矩形即可；控件重建时才进行一次完整只读重扫。两条路径都重新验证目标标题和会话指纹，只有就绪结果为真才接纳位置。窗口、进程、线程、客户端尺寸、DPI、活动代际与原生搜索凭证必须保持一致。当前会话的无搜索捷径、正文输入和提交阶段不使用这项布局迁移。

布局解析和辅助进程预热在后台进行。首次从旧配置生成 UIA 配置、或窗口尺寸变化时，布局包装器可能替换输入助手；新助手必须重新积累自己的用户活动观察时间，不能继承已退出进程的预热状态。`resolveLayout(job,{signal})` 可在空闲等待前完成这一步，随后在选定的新助手上运行焦点预检并等待空闲。正式队列将 `QT_ACTIVITY_WARMUP` 作为输入前的可等待拒绝；它不表示已经借用前台，也不能绕过活动保护。

已确认的同聊天连续文字发送可复用导航依据，跳过重新搜索。可选的标题指纹只读取指定标题子树中有限文本节点的 `Name`，在内存中计算摘要，不输出标题原文，也不读取消息列表或草稿。它同时保留标题容器和文本控件的运行时身份，结果明确为 `targetVerified:false`；摘要只帮助确认原会话未改变，不能代替原账号、联系人来源 ID 与目标身份核验，也不能凭任意相同标题批准发送。

文字回执基线仍在粘贴完成后、提交之前建立，时间窗口和唯一回执规则不变。基线请求现在与提交前的只读观察、UIA 核验并行；最终输入必须等待基线持久化完成，再检查当前权限、活动状态和原生一次性凭据。提前拒绝也会等候基线请求结束；只有明确未尝试输入的结果才能释放本次保留，异常或未知结果不会触发重发。

回执数据库连接由单个专用线程持有并复用，每次查询重新取数，不缓存回执结果或跨查询保留事务。每次都检查账号、选择范围、数据库分片及文件身份；分片增加或替换时重建连接，服务退出时关闭。文件助手测试接口已对齐正式服务的绑定回执协议，去掉额外两次往返；本机提交前回执准备从上一轮约 132 毫秒降至 10–12 毫秒。

控件定位复用原生控件引用，在每次操作内批量读取属性、共用祖先观察，避免重复完整遍历；缓存不是发送许可。编辑器确实已持有键盘焦点时直接复用，否则使用发给绑定微信窗口的客户区鼠标消息定位，不移动系统鼠标。图片发送、语音开始及提交也走定向消息；UIA 语音不再把鼠标移去标题栏停放，配置和执行请求均可省略 `mouseParkRect`，不补造占位坐标；旧 OCR 语音仍要求真实停放区域。消息成功入队只表示操作已请求，文本框焦点、录音实际状态与最终数据库回执分别确认结果，部分投递失败不重试。

UIA 执行帧使用独立的 `uia-metadata-v1` 格式，明确 `pixelsRead:false`，只携带真实控件身份摘要，不构造或冒充 RGBA 摘要。导航、文字、图片及恢复草稿的 UIA 分支使用这类帧；文字粘贴只读取刚写入的自身文本以确认剪贴板已消费，替代固定 60 毫秒等待，不输出内容。编辑器区域不携带空草稿证明。

## 已实现的范围

`scripts/native-ui/WechatAccessibilityGate.cs` 定位微信内置 Qt accessibility gate。默认检查只读；显式启用时，仅将精确绑定的微信进程内这一字节由 `0` 改为 `1`，随后读回确认。它不注入 DLL、不修改代码指令、不取焦点、不访问剪贴板，也不发送键鼠输入或消息。

UIA 本身是 Windows 提供的控件访问接口，不是内存注入。2026-10-31 用户明确允许修改这个无障碍开关字节，因此 UIA 模式保留受限的自动开启例外：先核验固定微信版本、程序及模块哈希、进程创建时间、窗口绑定和目标字节指纹，仅在值为 `0` 时写入一次 `1` 并读回确认；已有值为 `1` 时不重复写。这里确实存在受限的进程内存写入，不能描述为完全不写内存。后续发送仍通过 UIA、窗口消息及既有输入通道完成，没有 DLL 注入、内存发送或微信内部发送函数调用。

此前的媒体发送与离屏实测使用了已开启 gate 的微信进程，这些记录本身不证明新进程无需这个开关也能取得控件树。后续新进程的单独验证见下文。该授权只覆盖已固定、精确校验的单字节无障碍开关，不放宽其他注入或内存写入能力。

运行时现先通过标准 UIA 完整发现当前控件；成功则直接使用该结果，不检查或写入 gate。只有标准探测明确缺少微信控件树、额外只读遍历确认无 `mmui` 控件且窗口身份与输入状态稳定后，才进入上述已授权的固定版本开关流程，并重新验证完整控件；超时、身份或前台变化、用户活动、控件歧义均不触发这个补救步骤。

适配绑定以下证据：

- `state/ui-runtime/qt-visual.json` 中的程序路径、版本及程序摘要，实际窗口 HWND、所属 PID 和进程创建时间。
- 本版本 `Weixin.dll` 的 SHA-256：`e0428a7b691853de496532523c2c09aa095f90941c37c9f4cfb3f137f3c66556`。
- 唯一匹配的指令、`qt.accessibility.core` 引用及固定地址：gate RVA `0x0b39c9d8`、指令 RVA `0x00864af2`、字符串 RVA `0x09044528`。
- 已映射模块的对应指令与标识、目标地址所属映像，以及已提交、可写且不可执行的内存页。原字节须为 `0` 或 `1`。

多个候选、程序更新、进程或窗口更换、异常页面权限及指纹不符均拒绝写入；不依次试写未知地址。开启请求须回传检查所得完整绑定，开启前再次核验；原生入口还要求额外的显式写入开关。

`scripts/native-ui/WechatBackgroundControls.cs` 使用 UI Automation 读取这个精确窗口的控件树。记录节点类别、已知静态 AutomationId、可用操作模式、层级和几何等元信息；不读取控件的 `Name` 或 `Value`。其他 AutomationId 只保存摘要。每次记录节点/深度/耗时限制、是否完成遍历，以及前后台窗口、指针和输入时间的前后观察值；未完成的遍历不能解释成完整控件清单。

`scripts/native-ui/WechatBackgroundLayout.cs` 为 `--layout` 增加发送布局读取。搜索框须处于主聊天搜索区域；聊天编辑器须为 `mmui::ChatInputField` 且静态 AutomationId 为 `chat_input_field`。只对聊天输入工具栏中的指定按钮读取 `Name`、`HelpText` 或直接子标签，并仅输出静态白名单命中的文字。例如“发送”“发送文件”“发语音 ( 按住右 Alt )”。不读取联系人标题、聊天内容或草稿值。位置统一转换为客户端物理像素，保留负屏幕坐标，前后复核几何与根控件身份；多个匹配一律报告歧义。

`scripts/native-ui/WechatBackgroundVerify.cs` 为 `--verify-layout` 提供上述 3／5 角色的快速只读核验。它使用完整发现产生的定位路径，并重新校验真实控件身份和几何，不把路径序号或缓存矩形当成发送授权。定位依据失效时可以重新发现 UIA 控件；输入前仍须通过当前绑定和布局核验。请求显式启用 `includeConversationFingerprint`，或使用 `navigation-ready` 阶段时，才额外读取局部标题 `Name` 并返回摘要及来源控件身份；默认控件检查和布局发现不读取标题原文。导航就绪结果仍标为 `targetVerified:false`，只有上层的当前账号绑定、数据库唯一目标映射和本次原生窗口绑定共同通过，才能继续输入。

群聊标题摘要按已知完整静态 AutomationId `content_view.top_content_view.title_h_view.left_v_view.left_content_v_view.left_ui_.big_title_line_h_view.current_chat_name_label` 及其父角色定位，不把标题子树中的第一个文本当作群名。成员数字段是独立兄弟控件；完整会话指纹仍包含受限标题子树的文本摘要及运行时身份。只读校验失败仅保留白名单错误码；本次明确请求标题摘要后产生的标题读取标记不会被误判为输入行为，也不保存标题原文。

## 构建与使用

在项目根目录运行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/build-accessibility-gate.ps1 -SelfTest
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/build-background-controls.ps1 -SelfTest
node scripts/background-controls.mjs --hwnd <当前十进制微信主窗口句柄>
```

构建和自测不访问运行中的微信。最后一条命令默认只读，不会为了取得控件而修改 gate。确认当前绑定后，显式启用并检查控件树：

```powershell
node scripts/background-controls.mjs --hwnd <当前十进制微信主窗口句柄> --enable
```

包装器先检查固定版本，再将生成的绑定请求传给原生开启入口，随后读取控件元信息。控制台只输出摘要和本机报告路径；完整分阶段结果写入 `state/diagnostics/background-controls-*-result.json`。原生或 UIA 调用有独立子进程超时；开启阶段超时或结果不明确时会标记可能已经写入，不自动重复开启。

`npm run test:uia` 运行模式迁移、发送通道切换、控件包装器、布局绑定和服务保护的离线回归测试；它不发送微信消息，也不能替代三类消息的实机回执验收。

只读布局入口为：

```powershell
state/ui-host/WechatBackgroundControls.exe --layout --request <绑定请求JSON绝对路径>
```

请求包含 `{version:1,hwnd,pid,processCreatedFileTimeUtc,executable}`。结果包含 `binding`、`layout`、`voice`、`missing`、`ambiguous`，没有点击或发送授权；调用方须将绑定与本次原生窗口检查匹配。`missing` 中缺少独立图片按钮不影响图片粘贴路径，但搜索、编辑器、标题、发送、语音入口和工具栏必须齐全。

`prepare-ui-components.ps1` 已纳入两个新增组件，构建到 `state/ui-host/WechatAccessibilityGate.exe` 和 `WechatBackgroundControls.exe`；布局及快速核验 partial 源码随构建一并编译。常规运行检查把两项 UIA 组件列为可选，缺失不阻止原视觉模式；开启 UIA 模式仍要求组件齐全并完成实际控件检查。`checkNativeUiComponents({requireUia:true})` 可执行严格的离线组件检查。

当前 UI 部署继续通过 `secondary:export` 导出源码，在目标电脑重新准备组件、账号、音频及布局。源码包包含新增脚本和全部 C# 源码，不搬运本机 `state`、控件句柄或账号数据。安装后的组件和数据以本机配置为准。

可选的纯离线扫描只读取指定 DLL 文件，不访问微信进程：

```powershell
state/ui-host/WechatAccessibilityGate.exe --scan-file <本版本Weixin.dll的绝对路径>
```

原生检查接口为 `--inspect --request <JSON绝对路径>`；请求包含 `version:1`、`configPath` 和字符串形式的 `hwnd`。检查返回 `binding` 与 `candidateRequest`。原生开启接口为 `--enable --allow-gate-write --request <JSON绝对路径>`，仅接受上述检查生成的请求。通常使用包装器即可，不需要手工修改请求字段。

## 生命周期与发送通道

gate 只存在于当前微信进程内。保存的 UIA 模式选择允许发送服务在绑定新进程时重新核验并启用；独立诊断包装器仍要求 `--enable`。没有开机注入或系统级屏幕阅读器设置变更。关闭 UIA 模式停止该发送路径，不把仍由微信使用的 gate 清零；微信正常退出后该进程内状态消失。

独立诊断工具不改变机器人发送模式，模式切换由服务单独处理。`fullyBackgroundReady:false` 继续表示没有承诺完全无焦点运行；UIA 模式明确需要短暂前台操作和焦点归还。

旧版原生注入发送候选已随发送链路清理退役。

## 独立离屏位置探针实测（2026-10-31，生产接入前的历史）

`WechatUiaOffscreenProbe` 是独立诊断工具，不接入生产发送流程。构建脚本为 `scripts/build-uia-offscreen-probe.ps1`；默认只读检查。显式位置探针要求正式服务停止、取得统一输入互斥锁、精确绑定当前微信进程与窗口，并确认当前会话为文件传输助手。它保存窗口位置、还原矩形、最大化状态、DPI、前台身份及输入状态，再以不激活、不改变大小的方式将窗口移到全部屏幕范围以外；全过程不发送消息或键鼠输入，不访问剪贴板，不使用内存注入。

这个探针本身仍不是生产发送器；后续新增的 `WechatUiaOffscreenHost` 已负责正式窗口停放和恢复，完整发送验收见本文开头。离屏可减少遮挡，但本身不保证不会打断用户输入。

本机 `uia-offscreen-1031a-result.json` 记录表明：微信移到屏外后，编辑器、发送按钮、标题和语音入口仍可由 UIA 读取。离屏移动及控件读取期间，前台窗口、输入时间和鼠标位置均未变化。随后窗口外框、客户区、DPI、最大化状态、flags 和正常还原矩形均恢复到原值。这只证明本机当前窗口状态下的移动与控件读取可行，尚未证明屏外文字、图片、语音的完整生产发送通道，也不涵盖最小化、锁屏或任意显示器配置。

Windows 在回位时归一化了 `WINDOWPLACEMENT` 的最小化、最大化位置缓存，首份报告因此保留了严格元数据核验失败。恢复判断现区分 `semanticRestored` 与 `exactMetadataMatched`：实际窗口几何、DPI、flags、showCmd 和正常还原矩形仍须完全一致；只允许明确规则覆盖的缓存归一化，不为追逐旧缓存反复设置窗口位置。已有活动日志随后通过显式恢复命令完成只读确认，未再次移动窗口、设置 placement 或切换焦点；用户期间切换到的前台应用得到保留。具体记录保存在本机忽略的 `state/diagnostics/`，不随源码分发。

`scripts/build-uia-background-probe.ps1` 与 `scripts/build-uia-offscreen-probe.ps1` 及其 C# 源码随源码导出，可在目标电脑独立构建；它们不加入服务启动链。探针可执行文件、运行日志、发送尝试记录和机器窗口绑定均不导出。
