# 微信界面自动回复适配

## 当前实现与实机边界

Windows 微信 4.1.15.56 在无障碍开关关闭时，UI Automation 主要暴露外层窗口。2026-10-31 新增匹配本机精确版本的无障碍热激活与后台控件检查，已实机读到 `mmui::MainWindow`、搜索框和 `chat_input_field` 等真实控件；详见[后台控件适配](BACKGROUND_CONTROLS.md)。控件读取成功不等于账号身份或文字、图片、语音后台发送已验证。正式发送仍使用既有 Qt 视觉执行器。

新驱动接入正式 wechat-ui 后端、对象授权、持久队列和启动监督。离线验证覆盖身份变化、用户活动、草稿冲突、不确定提交、语音取消、重启与归档。2026-10-29 正式服务完成同一真实好友连续三轮：数据库入站、DSH 生成、界面文字发送、唯一数据库回执及上层完成记录全部一致，用户也确认收到回复。第一轮曾在准备阶段中断，修复后保留原任务 ID 恢复；后两轮直接成功。群聊真正被 @ 后的文字回复也已获数据库回执和用户确认。上述验证不替代长期运行、群语音或语音连续回复验收。显示组合的定位验收见 [显示验收矩阵](DISPLAY_ACCEPTANCE_MATRIX.md)；目前没有副机。

发送前长时间闪动的原因已定位到等待空闲时反复借还焦点：输入驱动与发送队列使用了不同的空闲门槛。修复后先在后台等待空闲与退避到期，再为当前消息取得焦点，并在提交前复用同一租约。`state/diagnostics/production-native-trace-20261029.jsonl` 的新版群回复样本记录 5 次文字提交、5 次取焦点和 5 次归还；不再出现旧流程等待期间重复切换。2026-10-30 用户已对新两轮好友自动回复确认“没有反复闪动，只短暂切换”，重复切换的观感验收通过；发送仍会短暂借用焦点。

2026-10-30 最新三条真实私聊回复均以一次借用／归还完成，含实际联系人搜索的连续占用为 1,282、1,032、1,219 毫秒，均取得唯一数据库回执，证据为 `focus-receipt-attribution-20261030-1793324460164.json`。这三条没有触发刚加入的连续导航复用，不证明省搜索后的现场耗时，也未达到每次一秒以内。

截至 `state/diagnostics/real-friend-replies-snapshot-1793253250577.json`，已选私聊完成 5 轮，群聊完成 7 轮、12 段回复，全部具有确认回执，快照中没有待处理回复；自动回复已恢复运行。该时段另记录一次含联系人导航的完整连续前台占用 1,328 毫秒，但该次没有逐步跟踪，不能与某一条回复建立严格的一一对应；此前有逐步跟踪的 5 次提交为 1,515–1,609 毫秒，当前仍不能声称每次都低于一秒。

界面模拟和数据库读取不能保证零检测或零风控。2026 年 10 月 29 日观察到现有微信要求重新登录，原因未知；当时没有重新启动微信，现场操作已停止。该提示不构成已确认封号的证据，后续登录由用户手动处理，详细记录见 [显示验收矩阵](DISPLAY_ACCEPTANCE_MATRIX.md)。

此前文件传输助手的文字与达妮娅短句已获真实回执，最后一次手机试听完整流畅；这是旧单次预览的历史证据，不能替代新自动队列的实机验证。

## 身份与草稿核验

QtVisualDriver 在本机已绑定的微信进程和当前核验布局中：

1. 检查前台、用户空闲、程序版本与哈希、尺寸和 DPI。
2. 核对微信进程打开的账号数据库，取得短时账号旁证。
3. 共享自适应私聊优先使用公开微信号；没有公开微信号时，只使用当前数据库中唯一映射到该联系人的备注或昵称搜索。内部稳定 ID 继续用于对象选择、授权和回执，不直接把内部 wxid 当作可搜索微信号。清空搜索框、粘贴后按一次专用 Return，不复制读回查询，也不额外打开资料或重开搜索；微信已经在前台时也沿用该快速流程。普通模式继续核对自身、私聊搜索行和好友资料。群聊按数据库中的完整群 ID 授权，再以新读取的唯一群名搜索；同名群或与联系人搜索名冲突时停止，不用 `@chatroom` 内部 ID 搜索。
4. 共享模式等待主窗与编辑区就绪，只记录进程、人工输入代次与标题/编辑区像素锚点；按用户选择不读取正文、不检查输入框是否为空。普通模式继续受控读取草稿并恢复原剪贴板。
5. 每次输入前复核状态；人类活动、失焦、遮挡、弹窗、窗口重建或像素改变使旧证据失效。

标题像素只用于发现会话变化，好友绑定来自当前账号数据库中的稳定 ID；公开微信号缺失时，备注／昵称仅在该数据库证明唯一的情况下作为搜索词。缺少账号证据或可用的唯一搜索映射时停止。备注／昵称回退已在一条真实私聊回复中取得唯一数据库回执，含导航连续前台占用为 1,375 毫秒；该单例不保证所有联系人或一秒以内；不增加界面身份核验或查询、正文读回。共享搜索 Return 后等待界面呈现：标题改变时，需要新的主窗标题／编辑区两帧稳定，间隔至少 35 毫秒；标题未改变时，先等待至少 350 毫秒，再采集两帧。见过新标题后不再接受旧标题作为完成依据，总等待最多 600 毫秒、18 次观察。它不增加 OCR、资料页或正文核验，也不是独立的第二次身份确认；350 毫秒不能保证任意迟延下都完成切换。

共享模式使用 `draftPolicy:'unchecked'`，文字和搜索粘贴显式设置 `readback:false`，语音会话的 `emptyDraftConfirmed` 为 false。原生结果只证明粘贴动作已执行和剪贴板已恢复，不证明当前正文与排队文本相同；已有正文、附件及用户修改不会在此模式下重新检查。普通模式的草稿读取仍是明确的选择/复制动作，空草稿需要读取与空模板同时成立，不把只读观察当作正文核验。两种模式的粘贴都保留完整剪贴板备份与恢复，不能完整保存或遭人工修改时停止。

同一对象连续回复时，成功文字提交后的导航记录可在 30 秒内复用一次，前提是账号、窗口、位置尺寸、DPI、用户活动及标题像素仍一致；不满足或被打断就重新搜索，不保留上一条正文或发送凭据。它随共享电脑模式启用，无需另设开关。同步授权内重复读取同一设置已合并，异步步骤后的授权仍重新检查。两处提速已通过 353 项相关离线检查；独立手动双消息实测分别占用 1,047 毫秒和 485 毫秒，第二条成功省去重复搜索，两条均有真实回执。该样本不属于模型自动回复，不能保证每次发送都低于一秒。

发送前的账号检查若明确尚未借用焦点、没有输入或待清理操作，失败时仅持久暂停发送、保留消息并让 Reader 继续运行，需手动恢复。原生拒绝原因只保留经过校验的固定代码。最后这项修复及相关队列边界共 416 项检查通过；正式服务已重新启用三个选中对象，先前中断的群回复已确认完成。完整故障、恢复及手动测试清理记录见 [显示验收矩阵](DISPLAY_ACCEPTANCE_MATRIX.md)。

群聊和好友均在“聊天”管理。自然参与模式会结合消息和上下文进行回复判断，“唤醒后回复”按原有唤醒条件处理，助手模式继续检查当前权限。群文字和原生语音使用同一群目标绑定，实际发送仍由各自的回执确认。

正式服务重连保留已生成回复及原发送 ID。网络断开、能力信息暂时缺失时继续等待并查询原回执，不重新生成或提交。焦点请求明确被拒、确认没有输入且已完成返回清理时自动退避；提交结果未知的消息继续只查询回执。

## 本机标定

配置通常位于 state/ui-runtime/qt-visual.json，绑定账号、程序版本/哈希、尺寸、DPI、搜索、资料页、编辑器和发送区域。自动查找窗口仅在精确程序绑定下进行，不代表忽略身份。

`qt-calibrate.mjs` 保留按本机矩形方案只读测量的首次配置与诊断入口。正式驱动在新任务边界发现宽高或 DPI 改变时，另用当前截图自动定位控件并复核像素，覆盖单独拉伸宽/高、同时拉伸，以及系统分辨率或缩放变化后的布局。它不在正在输入或已有待续输入时替换布局，不用旧坐标直接比例换算；未知版本、主题或不明确结果仍停止。支持范围与真实验收见 [动态布局候选](LOCAL_OCR_RUNTIME.md#动态布局候选)、[显示验收矩阵](DISPLAY_ACCEPTANCE_MATRIX.md)。每台机器仍需建立账号、程序和音频设备绑定；自动定位本身不授予发送许可，也不把共享模式标为已核验空草稿。

共享电脑短暂切换模式在新尺寸或缩放下被其他窗口遮挡时，会以 `SWP_NOACTIVATE` 临时置顶微信，取两张完整截图后撤销置顶；原前台、用户活动和窗口身份仍一致时，再把微信放回原先上方可见普通窗口的后方。只调整微信，不抬起或下移其他应用，也不移动或缩放窗口；当前路径要求微信主窗及附属窗口原本均非置顶。前台焦点保留，恢复后才进行图片编码、OCR 和控件定位，无需先手动调到微信或保存新布局。微信必须完整位于显示范围内；真人打断后仍撤销本次临时置顶，但不强行恢复焦点或重新排列用户的新窗口。尝试后仍有遮挡且已确认恢复时，只暂停发送，Reader 继续运行；恢复不明则保留错误。身份与遮挡检查仍有效，不复用旧坐标。

旧叠放实现曾在本机 DSH 遮挡下完成普通窗口和最大化窗口定位，显示至恢复为 78 和 94 毫秒；证据：[普通窗口](../state/diagnostics/layout-handoff-live-1793288379327.json)、[最大化窗口](../state/diagnostics/layout-handoff-live-1793288623005.json)（本地忽略目录）。2026-10-30 的新临时置顶路径先以 125 毫秒处理第三方 Unity 跨屏遮挡，但随后群置顶条定位失败；该失败保留。修复后，主屏 1605×777 @168 DPI 的群置顶条场景以 110 毫秒完成取图恢复，保持原前台、活动、位置尺寸与置顶状态，随后在后台完成全部定位，见本机 `layout-handoff-live-1793297453797.json`。窄 175% 的旧标题识别失败只有原图离线修复证据，未冒充同尺寸现场通过。这些数据只衡量取图显示干扰，不是联系人切换或发送耗时，不能据此宣称全部发送已经无感。

语音配置额外包含录音入口、录音控件的自动定位或固定模板、鼠标停放区和录音焦点。Qt 驱动先退出自己的输入进程并确认互斥释放，再交接短期录音会话；交接期间的真实输入变化由原生空闲时间标识再次检查。

## 队列与发送

| 环节 | 行为 |
| --- | --- |
| 接收 | 接收选中的私聊和群聊，保留事件 ID、名单版本和来源授权；群成员与群会话分开绑定 |
| 入队 | 固定本次文字或原生语音方式，共用同一桌面先后顺序 |
| 模型生成 | DSH 再核对来源授权；取消好友后旧回复失效，重新选择也不恢复 |
| 文字输入 | 普通模式按 Unicode 字素逐个模拟键盘；共享模式快速粘贴并恢复剪贴板，不读取正文 |
| 人工介入 | 搜索重跑；已完成粘贴但尚未执行发送的共享文字保留步骤，空闲后回到原聊天和输入框，只继续未执行的发送 |
| 提交 | 先持久化意图；共享文字消费本次粘贴动作的一次性证明后按一次专用 Return，普通模式点击发送；输入被接受不等于送达 |
| 回执 | 核对账号、完整目标、正文摘要或语音时长、服务器 ID 与新增数据库行 |
| 未知结果 | 发送已尝试或录音结束无法确认时只查回执或等待处理，不换 ID、重打、重录或改发另一种消息 |

换行只使用已核验的快捷键，不能与发送混为同一动作。所有聊天共享原生输入互斥，不同时打字和录音；后台推理可继续，桌面动作串行。

NativeVoiceOutbox 保存本次模型音频；NativeVoiceTransport 准备回执、取得新 Qt 身份会话、调用原生录音并查询结果。每段最多约 7.5 秒，拆分保留全部采样，整条回复使用相同合成模型。

选定私聊和群聊使用的生产原生协议与旧文件传输助手预览协议分开。原生执行器保持录音期限、专用音频线程、人工输入监听、标题像素和微信录音会话校验。播放只进配置的虚拟设备，不打开真实麦克风，不改变 Windows 默认音频；副机默认录音角色须预先指向对应 CABLE。

共享录音允许用户在其他应用内正常操作，提交前等待安全间隙。原有监测判定录音真正被打断（如用户返回微信）时停止播放；原录音归属仍有效、尚未尝试提交且可以取得焦点时，用一次 Esc 取消，不继续发送旧录音。仅在原生明确报告 Esc 已应用、录音已结束、没有发送尝试和录音屏障，且相关录音占用已解除后（文件传输助手预览还要求原读取组件退出），队列才保存旧尝试并以新 ID 等待空闲后重录同一段。取消失败、结果不全或已尝试发送时继续保留未知状态，不自动重录。发送仍点击微信录音发送按钮，语音 Return 提交实测未成功。

语音任务开始前的界面准备遇到用户活动时可等待条件恢复；普通模式仍可能因草稿冲突暂停。回执基线建立后的准备失败与已确认取消的录音分别处理，不把尚未录音的失败冒充取消完成，也不重录同一 ID。重录退避和旧尝试证据持久保存；停止服务、取消回复或撤销收件人会阻止下一次重录。取消重录分支已完成离线测试。文件传输助手 v8 在外部操作激活现有微信后，由原生 Esc 确认取消，未尝试发送；v9 另用新 ID 正常录制并取得回执。生产队列自动重录和连续真人键鼠干预尚未实测通过。

## 停止、恢复和长期容量

close 请求取消，drain 等待当前任务与原生进程实际退出。超时保留工作锁和录音状态；杀进程请求不是已退出证明。监督进程只有确认旧桥接与 Reader 结束后才启动新名单代次。

三类队列将已确认和安全取消的任务按 ID 前缀归档。日常只扫描有界活跃目录，历史按精确 ID 单文件查询；累计 256 条已完成任务不会停摆。归档保留绑定、输出方式和回执，旧 ID 不会再次发送。

未知提交、未知录音、部分输入和残留草稿不会靠归档解除屏障。已确认语音的 WAV 仅在哈希匹配时清理；取消音频保留。异常锁或状态损坏需要停服核对，不能删除记录后重发。

Reader 游标与发送 ID 分别持久化，桥接接收确认后才推进读取位置。离线后自动按分页进度补读，群聊和私聊均遵循当前聊天的参与方式、唤醒条件及助手权限。在“设置 → 诊断 → 读取记录修复”可查看补读进度。旧版中断事务可在停服后回滚原日志和游标，再由新版继续补读。发送不确定状态仍需按发送恢复流程核验。

## 验证顺序

先运行合成测试和离线状态机，再做只读窗口、布局与身份核验。通过后在明确测试聊天验证输入、暂停、一次发送和手机播放。模拟回执、构建成功和 HTTP 就绪都不等于实机发送成功。

    & .\scripts\build-qt-actions.ps1 -SelfTest
