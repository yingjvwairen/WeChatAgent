# Shared voice monitoring lifecycle

Shared voice uses the project's native input monitor before Qt preparation starts. This removes a new-monitor observation delay from the narrow interval after a fresh voice session is issued. Warmup itself retains the idle threshold, held-key checks, desktop/account/window and session bindings, recording-control templates and input-tick checks. The current shared path deliberately uses the database's complete WeChat ID with one search paste and Return; it does not open a profile for a second contact check, read back the query or body, or require an empty editor. Its session declares `draftPolicy:'unchecked'` and `emptyDraftConfirmed:false`; the ordinary foreground path retains its separate checks.

`warmVoiceMonitor({root, signal})`, exported by `scripts/timed-voice-preview.mjs`, starts the pinned local `state/ui-host/WechatVoicePreview.exe --private-warm`. The first private NDJSON request carries a fresh nonce. Readiness is accepted only after the native hooks and message pump run, with an exact nonce/monitor identity and explicit `readOnly:true`, `inputSent:false`, `mutexHeld:false`. This phase lasts at most 60 seconds and does not acquire the UI/audio mutex, activate a window, record, or play audio. User activity remains observable during preparation.

Pass the opaque returned handle as `warmMonitor` to `runTimedVoicePreview` or `runTimedVoiceSend`. Only one execution commit is permitted, bound to the same process, nonce, native monitor ID, mode and fully validated request. Native execution then acquires its mutexes and retains the existing 18-second watchdog. The ordinary foreground path is unchanged. `NativeVoiceTransport` performs this lifecycle automatically in shared mode. Custom test executors own their injected lifecycle; the real executor cannot disable warmup with a null factory.

Always `await monitor.close()` in the owner's `finally`. `close()` and `drain()` wait for actual process exit, not merely a cancellation request. An unused monitor gets EOF; a committed monitor receives cancellation. Cleanup escalation never proves that a recording was cancelled or sent.

A special native rejection can prove execution never began only when its exact nonce/monitor binding, four false ownership/input flags, and exit code 1 all agree. Then the attempt remains durably non-replayable, its active recording barrier can clear, and the preparation focus lease can be released after native exit. Missing, malformed, duplicate or interrupted output after commit retains uncertainty. Cancellation racing with a rejection is deliberately treated as uncertain. No automatic restart or fallback input occurs.

Optional pointer-return diagnostics contain only the complete boolean group `initialPointerRestored`, `finalPointerRestored`, and `pointerRestoreSkipped`; no pointer coordinates or other-app identity are persisted. Skipped pointer restoration does not imply a failed message or authorize another attempt.

The voice helper also observes left-button history during that existing warm phase. It establishes its own temporary return-window capability; it cannot receive a Qt caption capability in a request. Before starting the recorder, it must independently verify a visible title-bar neighborhood with `WM_NCHITTEST == HTCAPTION`, exact process/thread/window geometry and display coverage, no capture/menu/held keys, and safe double-click history. The neighborhood must be outside the frozen WeChat outer rectangle so bringing WeChat forward cannot hide it. Missing evidence refuses recording. No extra double-click wait is inserted while WeChat owns the foreground.

When the recording finishes in the background, the helper waits for the bounded safe input gap and establishes a new return capability for the then-current foreground app before borrowing focus. After actual WeChat focus is confirmed, it checks the entire client area for overlapping windows. If necessary, one guarded `SetWindowPos(HWND_TOP)` request is permitted without moving, resizing, making topmost, or reactivating the window. A raise already made by the calibrated activation fallback consumes this same allowance. The helper then rechecks full visibility and the original activity, process/thread, window geometry, audio capture session, desktop and modal-state bindings. It never substitutes a few clear button points for this whole-window proof.

For each return capability, the helper makes at most one ordinary foreground request and, only when WeChat still owns the foreground and all evidence remains valid, one real title-bar click. It rechecks both threads' capture state and title-bar semantics immediately before that click, synchronously records the click intention to prevent delayed hook callbacks from hiding double-click risk, confirms the actual resulting foreground, then restores only its own untouched pointer. It does not raise the other application, join input queues, inject memory, or send a virtual activation key. A different foreground window or changed activity cancels that return attempt. Uncertain recording or submission retains its barrier and cannot be resent. For an actual interruption of a bound recording before any submit attempt, the separate cancellation path may apply one Esc and observe that same capture session ending; only the complete cancellation facts allow the queue to wait for idle and create a distinct recording attempt. Normal background activity in other applications remains allowed under the existing shared-mode rules.

Optional `initialCaption` / `submitCaption` diagnostics contain five booleans only. Optional `submitVisibility` contains bounded timing/counts and an allowlisted result; no caption coordinates, window handles, process identity, or reusable capability enter the public or durable report. Foreground intervals include the visibility request, confirmation, return and pointer cleanup, including unsuccessful attempts.

Voice183 removes the shared path's repeated fixed 200 ms pointer-park waits. Before recording, two matching actual idle-region observations at least 20 ms apart replace the first wait, within the original 200 ms limit. Existing capture and recording-UI readiness still precedes playback, and actual end observation still follows submit. Ordinary foreground waits are unchanged.

Offline coverage includes `test-voice-warm-monitor.mjs`, `test-timed-voice-preview.mjs`, `test-native-voice-transport.mjs`, `test-native-voice-outbox.mjs`, and `test-ui-voice-preview-submit.mjs`, plus the native synthetic self-test. The current native helper also completed real file-transfer-assistant runs on 2026-10-29. The unique database voice receipt and decoded audio were 5100 ms, with the full 4560 ms source covered and no new silent gap. Cleanup and all six existing default audio roles were verified unchanged; the selected CABLE route remains in place. These diagnostics use a private native exception for the Chinese file-transfer-assistant search query, not a real private-friend automatic-reply acceptance.

In V12, externally activating the existing WeChat window interrupted the bound recording and automatic Esc cancellation succeeded without a submit attempt. Its 63 ms cancellation interval begins with WeChat already foreground and excludes that external activation. Final V2 subsequently recorded under a distinct ID. This validates those controlled cases, not production queue automatic rerecording, sustained human interference, the full DSH reply loop or secondary-machine deployment. Earlier text V5 measured a complete 813 ms navigation/paste/Return/return interval with driver `3beb6a48b8bd`. No single-run timing is a general sub-second guarantee; automatic replies remain disabled on this machine.
