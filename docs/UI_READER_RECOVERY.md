# 离线消息自动补读

机器人恢复运行后，会从上次持久化的读取位置接续扫描当前已启用聊天的微信数据库，分批补读期间收到的消息。补读进度与事件记录一同保存，中途停止后可继续。

- 同一聊天一段离线期间收到的消息会一起补读。读取完成后，机器人按该聊天的参与方式、唤醒条件和助手权限，选择最近一条符合条件的发言判断一次。更早的消息作为上下文，聊天人格可以选择接最后的话题或保持沉默。
- 图片、表情、语音、视频、引用与转发沿用消息身份和附件绑定。只有当前允许的聊天会被读取。
- 每条消息保留稳定 ID。桥接确认接收后才推进游标，重复扫描不会重复入队。
- 第一次启用某个聊天名单时建立当前基线。补读覆盖该名单已有读取记录之后的离线区间。

在「设置 → 诊断 → 读取记录修复」查看上次完成扫描的时间、已接收待确认消息数，以及正在补读的聊天进度。服务运行后自动补读，无需设置补读开关或点击重建基线。

微信数据库中的消息和附件需要仍然存在。缺失分片、读取失败和游标异常会显示错误并保留原记录，程序不会用跳到当前时间代替补读。发送侧的草稿、录音或未知提交状态按各自恢复流程处理。

## 兼容旧版中断事务

旧版「重建读取位置」可能在写入日志与游标之间中断。遇到此类记录时，页面提供还原入口。先停止服务，检查预览后确认还原，程序在独占锁下将原日志和游标逐字节恢复。随后启动新版服务即可自动补读。原始备份保存在本机 state/reader-service/recoveries 目录。

正常情况下，旧页面提交 acknowledgeGap 请求会收到「自动补读」说明，日志和游标保持原位置。只有实际存在旧版中断事务时，确认请求才会执行回滚。

## 本机接口

- GET /api/ui-reader-recovery 返回首次读取、待补读、当前补读进度或正常状态。摘要包含 available、firstRun、gapDetected、backfillActive、lastScanAt、pendingCount、revision、busy 和可选的 backfillProgress。
- incompleteRecovery 为 true 表示旧版事务需要还原。canRecover 仅在该事务存在且服务已停止时为 true。
- POST /api/ui-reader-recovery 仅用于旧事务还原，提交 expectedRevision 和 acknowledgeRollback:true。为兼容已经打开的旧页面，实际存在旧事务时也接受 acknowledgeGap:true。
